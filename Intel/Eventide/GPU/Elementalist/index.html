Arc Elementalist · Xe5 · RTU5
ELEMENTALIST
Xe5

Every dedicated flagship shipped so far is a card you add to a machine. Elementalist is the machine's GPU — and it does not iterate on the last generation, it redraws the line. A photonic network of Xe5 tiles that presents to the operating system as one coherent device: a single fanless tile in a thin-and-light, four tiles fused over FOveros 2.0 in a 2,000 W workstation, the same architecture at both ends. Wider cores with out-of-order wave dispatch and FP8-through-FP64 vector width. A matrix engine that retires the add-in AI accelerator. And a ray tracing unit that stopped building trees — it only intersects them now, and everything else moved to silicon built for it. One architecture, the whole GPU segment, on Intel 04A. Unified as one.

01
SHADER ARCHITECTURE · GENERATION 5
Xe5 Core

The Xe5 shader core is the widest, deepest execution unit Intel has ever built for graphics. Each Xe5-core contains 512 unified shaders — double the 256-shader Xe4E — organised into 32-wide wavefronts with out-of-order wave dispatch. The front-end decodes up to 4 instructions per clock per wavefront, feeding a 512-entry reorder buffer so waves execute non-sequentially by data readiness — a CPU-microarchitecture technique that lets a wave stalled on a cache miss yield to a wave with data ready, eliminating the pipeline bubbles that plague in-order GPU schedulers. Feeding those lanes is a new 16 KB private L0-data cache per core, straight into the 32-wide wavefront ports, backed by a 192 KB L1 (up from 128 KB) and the per-16-core-cluster L0 instruction cache.

Riding those same ALUs is XeAVX-2048 — a 2048-bit-wide vector ISA extension, distinct from the matrix-only XMX5, that spans the entire precision range in one unit. At the low end it packs FP8 / INT8 / FP16 at 2×/4× rate per lane for shadows, particles and post-process; at the high end it runs native FP64 at 1/2 FP32 rate, not emulated through FP32 pairs. That width is what makes the E1080's double-precision throughput workstation-real rather than a checkbox: the same silicon that shades a game frame runs HPC-class FP64 vector math, no discrete compute card required. Against the Xe2 generation in Battlemage, the Xe5 core retires 2.2× the instructions per clock.

Xe5 Raster · The Architecture Behind The Number
5× per tile is no longer an assertion.

The raster specs were always here; the technology that earns them was not. Xe5 fills that gap with a tile-based binning front-end, Nanite-class virtualized geometry, variable-rate shading driven by the scheduler's own predictive model, feedback-streamed textures, and a wide low-precision shader ISA — each contributing a measured multiplier that compounds to the published ~5×/tile → 20× across ×4.

Tile-Based Binning Rasterizer
Kachelraster Engine

Geometry is binned into 64×64px tiles and overdraw-culled before shading, using a 2 MB on-die bin buffer per raster cluster (shared with L2). Fragments that would be occluded never enter the shader array — roughly 40% less overdraw and 35% bandwidth saved versus immediate-mode rendering.

AI MATRIX ACCELERATION · GENERATION 5
XMX5

XMX5 is the most significant generational leap in Intel's matrix acceleration history. Each XMX5 unit delivers 2× the throughput-per-clock of XMX4E at equivalent precision, but the real story is precision expansion. XMX5 introduces native INT2 and FP4 execution — sub-byte precisions that quadruple effective throughput for quantized AI models. For XeSS 5.0 frame generation, the XMX5 units generate entire intermediate frames using a temporal neural network that runs at native resolution, eliminating the artifact-prone upscaling step used by competing solutions. The dedicated 512 KB L1 AI SRAM per XMX5 cluster holds model weights locally, avoiding the memory bandwidth wall that limits matrix throughput on traditional architectures. Sparse activation skipping — where zero-valued matrix elements are detected and bypassed in hardware — delivers up to 1.8× effective throughput on real-world models with typical 40–60% sparsity.

04
RAY TRACING · GENERATION 5
RTU5

RTU5 is not a new ray tracing unit — it is the same generation-5 traversal silicon with a substantially expanded capability set. At its core it still implements fourth-order bounding volume hierarchy (BVH4) traversal, where each node carries four children instead of the industry-standard two, halving tree depth for equivalent scene complexity. Hardware ReSTIR resamples hundreds of candidate light paths for converged global illumination at a fraction of a brute-force ray budget, and stereo BVH caching re-traverses one acceleration structure for both eyes in VR. What changes this generation is everything around traversal: RTU5 now performs only ray–AABB and ray–triangle intersection. It never builds trees. BVH construction, refit, pruning and residency are lifted off the traversal units entirely — split across the Symbiotic BVH Pipeline, the Kache Kore Prune Array, Persistent Hierarchy Residency, and the Photonic Ray Mesh — so the intersection hardware runs closer to its theoretical peak instead of stalling on structure maintenance. Motion vectors, GI probe evaluation, contact shadows and multi-bounce proxy rays each get their own fixed-resolver, moving closed-form math out of shader code and into dedicated silicon.

RTU5 · Expanded Capability Set
Traversal intersects. Everything else moved.

BVH work is two problems with different latency profiles, and RTU5 stops pretending they are one. The Symbiotic BVH Pipeline splits the tree-critical path from the bulk leaf refit and routes each to the core class physics favors. Rays that will miss are killed inside the cache before they ever reach an execution unit. Static world geometry is pinned across frames. And four tiles trade ray and node work as one engine over the existing photonic fabric.

Before dispatch, the KPA pruning ALUs test each ray against bounding boxes inside Kache Kore's SRAM bitlines. Misses are discarded in-cache; only survivors reach RTU5 traversal — the visible hit/miss branch of the pipeline.
Tier-Scalability · Feature-Uniform, Quantity-Scaled

Per the Eventide family table, Core 500 has no Compute Tile, Core i500 has a Compute Tile but no SPE cores, and Core Ultra 500 carries only limited SPE. SBP Stage 2 is therefore not SPE-exclusive: on tiers without SPE it falls back to idle LPE (Darkmont) cores. Every tier runs the same SBP behavior — same two-stage split, same profile-aware routing — with less parallel throughput lower down the stack, never a different or absent feature. Stage 1's target likewise follows the active AFFINITY profile (DP under Performance/Unleashed, UHE under Balanced/Efficiency), an extension of Thread Director's existing profile-aware dispatch rather than a new mechanism.

Near-Memory Compute
Kache Kore Prune Array
Low-precision ray–AABB pruning ALUs embedded directly in Kache Kore's SRAM bitlines. Rays that miss a bounding box are discarded inside the cache, before ever reaching an RTU5 execution unit. The pruning logic physically sits in the tile-level L3, ahead of an L4 miss.
KPA
Cross-Frame Residency
Persistent Hierarchy Residency
Static world-geometry BVH stays pinned in Kache Kore's 4 GB across frames; only dynamic subtrees get refit by SBP each frame. The same residency mechanism is reused by Feingeometrie's geometry-cluster caching and by the GI-proxy BLAS — one cache infrastructure, several pipelines.
PHR
Multi-Tile Coherence
Photonic Ray Mesh
Extends Foveros 2.0's existing tile arbitration — already unifying the raster framebuffer and command queue across ×4 E1080 tiles — to ray and BVH-node dispatch. All four tiles trade work as one coherent RT engine. Uses established Foveros 2.0 numbers: 448 Tbps, −70% latency vs copper, 0.08 pJ/bit. No new interconnect physics.
Photonic Ray Mesh
Fixed-Resolver Additions
Closed-form math, moved to dedicated silicon.

The same design principle the platform already applies to fixed-function acoustic compute — closed-form geometric terms evaluated in dedicated silicon rather than shader code — applied here to graphics. Each resolver replaces a screen-space approximation or a redundant pass with an exact, near-free evaluation.

Motion · from path length
Free Motion Vectors
RTU5 traversal already computes high-precision hit distance per ray for BVH4. Retaining that value's frame-to-frame derivative hands XeFG 3.0 / XeSS 5.0 a motion-vector source with no separate G-buffer motion pass — nearly free, because the traversal payload already carries it.
Indirect lighting
SH Probe Resolver
Fixed-function spherical-harmonic matrix multiply for irradiance-probe evaluation — a direction-to-SH-weights operation evaluated in dedicated silicon rather than shader code, for indirect-lighting probes.
Contact / silhouette
Silhouette Fixed Resolver
Closed-form geometric term for contact shadows and silhouette softening at flagged edges — flagged at bake time, evaluated only where flagged — replacing the screen-space multi-sample approximations (PCF-style hacks, SSAO) most engines use here.
Multi-bounce indirect
GI-Proxy Decimated BLAS
A coarse, decimated proxy tree for multi-bounce indirect rays — which don't need triangle-level fidelity — cached via PHR alongside the full-fidelity primary-ray BVH.
05
MEMORY ARCHITECTURE · KACHE KORE + ZAM
Unified Memory

A discrete GPU carries its memory. Elementalist inherits the platform's. Six tiers — L0 through the Kache Kore L4 and out to terabyte-class ZAM — collapse into one coherent hierarchy with no PCIe wall anywhere in it. The centerpiece is Kache Kore: a 4 GB bLLC (bandwidthLLC) fabricated on Intel 04A alongside the compute tiles. For the GPU, Kache Kore acts as an enormous L4 cache that absorbs the working set of most 1440p and many 4K game frames entirely on-package, eliminating the latency penalty of DRAM round-trips. Each Xe5 tile maintains its own L2 cache (12 MB/tile, 48 MB total across ×4 E1080) plus a new 24 MB tile-level L3 shared across the Xe5-core clusters, RTU5 and XMX5 — where the KPA pruning logic sits before a miss falls through to Kache Kore — with hardware cache coherency across tiles via FOveros 2.0. When a tile's L2 misses, the request hits Kache Kore at ~8 ns latency — comparable to dedicated GDDR7 on discrete GPUs — before falling through to Intel Z-Angle Memory (ZAM) mounted directly on the FOveros 2.0 photonic substrate. Unlike conventional DDR6/LPDDR6, ZAM is bandwidth and density-optimized for sustained high-throughput workloads, delivering 2–3 TB/s per controller and an effective 5–6 TB/s across both dual-channel ZAM controllers — dwarfing the bandwidth envelope of any discrete GDDR7 stack. Smart Memory Tiling automatically pins frequently-accessed texture mipmap levels and shader constants in Kache Kore, ensuring that bandwidth-critical data stays on-package.

L0d · 16 KB/core, private (NEW). A dedicated data cache that feeds the 32-wide wavefront ports directly. Previously the hierarchy had no L0-data tier at all — the nearest data lived in L1. L0d shortens the path from cache to lane, keeping the wide shader front-end fed without an L1 round trip on every access.

It is the seam between the compute tiers and the on-package bLLC.
L4 · Kache Kore, 4 GB bLLC (unchanged). The on-package bandwidth LLC at ~8 ns. It absorbs whole 1440p and many 4K frame working sets, holds PHR's pinned static BVH and Feingeometrie's cluster hierarchy, and is the destination SBP streams completed nodes into.

PROCESS NODE · MULTI-TILE PHOTONIC FABRIC
Intel 04A + FOveros 2.0

This is the seam where four tiles stop being four. The Xe5 GPU tiles are built on Intel 04A — the same world-leading node as the Eventide Compute Tile — but the part that has no precedent is FOveros 2.0: a second-generation photonic interconnect that binds up to four GPU tiles into a single coherent device, and means it — one memory space, one command queue, assembled from four dies over light. Unlike organic substrate interconnects that measure latency in nanoseconds and bandwidth in hundreds of GB/s, FOveros 2.0 uses on-package silicon photonic waveguides to deliver sub-2-nanosecond tile-to-tile latency at over 3.2 TB/s aggregate bisection bandwidth. The operating system and application see one GPU, one memory space, one command queue. Shader work distribution across tiles, cross-tile L2 cache coherency, and synchronized display output are all handled in hardware by the FOveros tile controller — with zero driver overhead. This is not SLI. This is not CrossFire. This is one GPU, built from four tiles, with single-GPU programming semantics.

The Elementalist Idea · A GPU That Is A Network
Bolt grows a card.
Elementalist grows a network.

This is the GPU expression of the Eventide idea. Eventide is one vertically integrated package that spans 0.5 W to 2,000 W — a phone's efficiency and a server rack's power on the same silicon — and the Elementalist makes that move for graphics: a photonic network of Xe5 tiles that presents to the OS as one coherent GPU, from a single fanless tile in a thin-and-light up to four tiles fused over Foveros 2.0 in a 2,000 W workstation. It does not hang off the PCIe bus as an add-in board — it is part of the machine, drawing the platform's unified terabyte-class ZAM straight as VRAM.

Bolt's Zeus scales the other direction: a discrete accelerator that grows by making one card bigger and bolting on more LPDDR5X, for one job — offline path tracing. That is a genuine strength in its lane, and it is a point solution where the Elementalist is a whole segment. On the two axes Zeus markets hardest — the memory ceiling and FP64 — the top Eventide platform meets or beats it (FP64 is XeAVX-2048's fight, and it is 2048 bits wide); on real-time ray tracing, the workload the Elementalist is built for, it is not close. Every Zeus figure below is Bolt's own published claim.
